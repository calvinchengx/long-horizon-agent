# The UI API contract

`openapi.json` (OpenAPI 3.1) is the only definition of the API every implementation's `lha serve`
provides to the mission UI and MCP clients ([docs/27-mission-ui.md](../../docs/27-mission-ui.md)).
It is written before server code; a server is built to pass it.

| File | What |
|---|---|
| `openapi.json` | operations, request and response schemas, security; `MissionEvent` payloads `$ref` [`../obs/mission_events.json`](../obs/mission_events.json) |
| `fixture.json` | the store rows and anchors every case runs against (generated by `python/scripts/export_spec.py`) |
| `cases.json` | one case per behaviour: a request and its expected status, error code and body |
| `mcp.json` | the operations as MCP tools, and the operations that are not tools and why (generated from `openapi.json` by `python/scripts/export_spec.py`, which also writes each implementation's embedded copy) |
| `mcp_cases.json` | the MCP cases: a JSON-RPC message and its expected result or error |
| `check-breaking.sh` | fails when `openapi.json` breaks a client of a base commit's API within the same major version |

## Coverage

- **Static, in every unit run** (`test_every_ui_api_operation_and_status_has_a_case`): every
  operation and every response status it documents has a case; every case names a documented
  operation, path and status; the fixture records every event kind.
- **Against a running server** (`python/tests/serve/`): every case's response matches its status,
  its error code and its body, and validates against the operation's response schema (so every
  recorded event is checked against its kind's schema). CI runs it against each implementation's
  server, once with Temporal unreachable and once with a fake mission workflow.
- **No undocumented routes**: each implementation tests that the routes it registers are exactly
  the paths in `openapi.json`, and an unknown `/api/` path is a 404 `not_found`.
- **MCP** (`test_every_operation_is_an_mcp_tool_or_refused_and_every_tool_has_a_case`): every
  operation is exactly one tool or one of `not_tools`; `decideGate` and `abortMission` are never
  tools; a tool's arguments are its operation's parameters and body; every tool has a successful
  case and every protocol method a case; each implementation's copy of `mcp.json` is current.
  The runner plays every MCP case over the server's `/mcp` and over `lha mcp`, and checks each
  tool result's `structuredContent` against its operation's response schema.
- **The servers' code, completely**: CI fails unless the conformance runs, plus each
  implementation's own tests of what no case can reach (a failing store, a client gone
  mid-stream, a Temporal error other than "no such workflow"), cover every line and branch of
  Python's `lha.serve` and every statement of Go's `internal/serve`. The Go binary under test is
  built with `-cover`. A new implementation adds the same gate for its server.
- **No breaking change**: within a major version (`info.version`) the API only grows. CI runs
  `check-breaking.sh <base>` (oasdiff) against the previous commit's or a pull request's base's
  contract; removing or renaming anything a client reads, or requiring anything new, fails it.
  Linted with Redocly.

## What a server must do to be tested

The runner starts the server with `<command> --host 127.0.0.1 --port 0` and this environment:

| Variable | Meaning |
|---|---|
| `LHA_SQLITE_PATH` | the seeded mission store (`LHA_POSTGRES_DSN` is unset) |
| `LHA_SERVE_TOKEN` | the token to accept (otherwise the server makes a random one) |
| `LHA_TEMPORAL_ADDRESS` | Temporal: unreachable, or a dev server running the fake workflow |
| `LHA_SERVE_KEEPALIVE_S` | how long a quiet stream waits before it sends a comment (default 15; the runner sets 1) |

Its first line on stdout is `lha serve: http://127.0.0.1:<port>/?token=<token>`. It answers MCP at
`POST /mcp` (the token as `X-LHA-Token` or `Authorization: Bearer`). The stdio server
(`LHA_MCP_CMD`, e.g. `lha mcp`) gets the same environment, reads JSON-RPC messages one per line on
stdin, writes one response per line on stdout, and exits when stdin closes or on Ctrl-C. Both
stop cleanly (exit 0) on Ctrl-C, and `--host` other than loopback exits 2.

The fixture's missions cover each shape the API distinguishes: a local run, a durable mission (the
fake workflow), a finished one, one whose anchor is on another host, one whose workflow no longer
exists and whose anchor's checklist does not parse (`"anchor": "$broken"`), one with more
events than a page (`bulk_events`: `count` copies of an event, recorded after `events`), and one
whose item has a failed attempt kept under `refs/lha/attempts/` (an anchor's `attempts` list seeds
the candidate commit).

## Cases

```json
{"name": "...", "operation": "listEvents",
 "request": {"method": "GET", "path": "/api/v1/missions/mission_local/events",
             "query": {"limit": "2"}, "auth": "header", "host": "...", "headers": {}, "body": {}},
 "expect": {"status": 200, "body": {...}, "error": "not_found", "signal": {...}, "stream": {...}},
 "temporal": "absent"}
```

- `auth`: `header` (the default: `X-LHA-Token`), `cookie` (`lha_token`), `none`, or `wrong`.
- `host`: the `Host` header to send instead of the server's own.
- `body`: JSON, or `"$not-json"` for a body that does not parse.
- `expect.body` is a subset of the response: objects match key by key, a list matches element by
  element and in length, `"$any"` matches any value, `{"$len": n}` a list of length `n`, and
  `{"$contains": [...]}` a list holding an element matching each one.
- `expect.error` is the `error.code` of an error response.
- `expect.signal`: the signal the fake workflow must have received (`{"name": "$cancel"}`: the
  workflow was cancelled).
- `expect.stream`: what a Server-Sent Events stream sends first: `mission_event` messages, in
  order (or `{"$len": n}`), `mission` messages, and `keepalive: true` for a comment. With
  `append` (events) or `touch` (`{"mission_id", "status"}`), the runner records those events or
  changes that mission's row once the stream is open; those cases run last.
- `temporal`: run only with Temporal `absent` or the fake workflow `running`; no value runs in both.

## MCP

Each tool of `mcp.json` is one operation: its `arguments` say where each argument goes (`path`,
`query` or `body`), and its `inputSchema` is generated from the operation's parameters and body. A
server sends a call through its own routes as an authorized local client, so a 2xx response is the
result's `structuredContent` (and its text, as JSON) and an error response is a result with
`isError: true` whose `structuredContent` is the API's error body. Protocol errors are JSON-RPC
errors: `-32700` a message that is not JSON, `-32600` one that is not a JSON-RPC 2.0 request (both
HTTP `400` on `/mcp`), `-32601` an unknown method, `-32602` an unknown tool, a missing or
unexpected argument, or a path argument that is not a non-empty string. A notification gets no
response (HTTP `202`). `initialize` answers with the client's protocol version when the server
speaks it, otherwise its own (`protocol_version`).

```json
{"name": "...", "request": {"body": {"jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {}},
                            "auth": "bearer", "host": "...", "method": "GET"},
 "expect": {"result": {...}, "error": {"code": -32602}, "tool_error": "not_found", "status": 400,
            "id": null, "no_response": true, "signal": {...}},
 "transport": "http", "temporal": "running"}
```

- `request.body`: the JSON-RPC message (`"$not-json"` for one that does not parse); `auth`, `host`
  and `method` apply over HTTP only (`auth` as above, plus `bearer`).
- `expect.result` and `expect.error`: subsets of the response's, with the markers above;
  `{"tools": "$spec"}` is `mcp.json`'s tools exactly as `tools/list` must list them.
- `expect.tool_error`: the result has `isError` and this `error.code`.
- `expect.status`: the HTTP status (default `200`); `no_response`: nothing is answered.
- `transport`: run only over `http` or `stdio`; no value runs over both.
